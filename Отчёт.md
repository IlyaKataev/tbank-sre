# Отчёт: T-Bank SRE Marketplace

## Доменная область

Приложение представляет собой небольшой маркетплейс. Продавцы управляют товарами, покупатели просматривают каталог. REST API дополнительно позволяет создавать и изменять заказы, отменять их с возвратом остатков и применять промокоды.

Веб-интерфейс реализует полный сценарий управления товарами: регистрация/вход, создание товара, просмотр списка и карточки, редактирование, архивирование. Есть фильтры по статусу и категории, пагинация и восстановление товара из архива через редактирование.

Удаление логическое: `DELETE /products/{id}` устанавливает `ARCHIVED`. Запись сохраняется для истории заказов, но не входит в активный каталог. Продавец может изменять только свои товары. Пользователь с ролью покупателя не имеет прав изменения каталога. Через публичную регистрацию доступны только роли USER и SELLER.

## Стек и архитектура

- Backend: Go 1.26, HTTP/1.1 REST, chi, pgx, sqlc, oapi-codegen, golang-migrate, zerolog.
- Frontend: HTML, CSS и JavaScript без внешних библиотек и CDN. Файлы встроены в Go-бинарник через `go:embed` и обращаются к API на том же origin.
- Хранилище: PostgreSQL 18.3. Пароли пользователей хешируются bcrypt; refresh-токены хранятся в БД в виде хешей.
- Упаковка: многостадийный Dockerfile, Docker Compose. Обычный стенд состоит из сервера и PostgreSQL, перед запуском сервера завершается одноразовый мигратор.
- Для демонстрации горизонтального масштабирования предусмотрены две реплики сервера и Nginx из дополнительного Compose-файла.

Фронтенд и бэкенд — отдельные логические части одного приложения. Совместная упаковка не требует отдельного Node.js-сервера и уменьшает расход ресурсов. Встроенная статика одинакова у всех реплик.

## Основные сущности

| Сущность | Назначение |
|---|---|
| Пользователь | Email, хеш пароля, роль USER/SELLER/ADMIN |
| Товар | Владелец-продавец, название, описание, категория, цена, остаток, статус |
| Заказ | Покупатель, статус, общая стоимость и скидка |
| Позиция заказа | Связь заказа с товаром, количество, цена на момент заказа |
| Промокод | Процентная/фиксированная скидка, срок действия и лимит использований |
| Refresh-токен | Хеш токена, пользователь и срок действия; обеспечивает общую авторизацию между репликами |
| Операция пользователя | История операций для ограничения частоты действий с заказами |

Схема и ограничения: [`internal/migrations/000001_init.up.sql`](internal/migrations/000001_init.up.sql). SQL-запросы: `internal/db/queries/`. При изменении и отмене заказа строка заказа блокируется внутри транзакции до проверки состояния, чтобы параллельные отмены не возвращали остатки дважды.

## Соответствие 12 факторам

Основание — методология из семинара и [The Twelve-Factor App](https://12factor.net/ru/).

### 1. Кодовая база

Один Git-репозиторий содержит исходники фронтенда, backend, миграции и описание запуска. Разные окружения разворачиваются из одного коммита. Первый коммит фиксирует исходную реализацию; дальнейшие коммиты показывают доработки для SRE. Разветвлённые копии кода для разных окружений не нужны.

### 2. Зависимости

Зависимости Go объявлены в `go.mod`, содержимое проверяется через `go.sum`. Версии генераторов закреплены: oapi-codegen `v2.8.0`, sqlc `v1.31.1`. Версии базовых образов и PostgreSQL заданы явно. Docker изолирует окружение; генерация и компиляция выполняются в образе Go 1.26.1. Runtime не зависит от установленного на хосте Go/Node.js. Фронтенд не скачивает сторонние шрифты или скрипты.

Доказательство: [`Dockerfile`](Dockerfile), [`Makefile`](Makefile), [`go.mod`](go.mod), [`go.sum`](go.sum).

### 3. Конфигурация

DSN, JWT-ключ, порт, сроки действия токенов, уровень логирования и таймауты читаются из переменных окружения. Обязательная конфигурация и некорректные значения проверяются до запуска сервера. Секретов по умолчанию в коде нет. `.env.example` не содержит рабочих секретов; `make env` создаёт уникальные локальные значения, `.env` исключён из Git, Docker build context и сдаваемого архива.

Доказательство: [`internal/config/config.go`](internal/config/config.go), [`.env.example`](.env.example), [`scripts/init-env.py`](scripts/init-env.py).

### 4. Сторонние сервисы как подключаемые ресурсы

PostgreSQL подключается по `DB_DSN`. Для замены локального экземпляра на другой совместимый PostgreSQL достаточно изменить DSN и применить миграции. Сетевая БД находится вне процесса приложения. Это не означает произвольную замену PostgreSQL на несовместимую СУБД без изменения SQL.

Доказательство: [`internal/db/db.go`](internal/db/db.go), [`docker-compose.yml`](docker-compose.yml).

### 5. Сборка, релиз, запуск

Build генерирует Go-код, компилирует сервер и мигратор, встраивает frontend/SQL в артефакты. Release — готовый образ с тегом коммита плюс конфигурация окружения. Run запускает этот образ без компиляции, правок кода и установки зависимостей. OCI-метки содержат версию и revision. `make build VERSION=<commit>` и `make up VERSION=<commit>` разделяют стадии; для отката приложения можно использовать сохранённый прежний образ при совместимой схеме БД. Тег `local` предназначен только для разработки; релизные теги не переиспользуются.

Доказательство: [`Dockerfile`](Dockerfile), [`Makefile`](Makefile), раздел запуска в [`README.md`](README.md).

### 6. Процессы без локального состояния

Товары, пользователи, заказы, refresh-токены и история операций хранятся в PostgreSQL. Память процесса содержит только конфигурацию, соединения и временные данные запросов. Веб-сервер не хранит локальные пользовательские файлы или серверные сессии; runtime-контейнер работает с read-only filesystem. Перезапуск сервера не теряет прикладные данные. PostgreSQL использует отдельный именованный том, подключённый к правильному для PostgreSQL 18 пути `/var/lib/postgresql`.

### 7. Привязка портов

Go-приложение само слушает HTTP-порт из `HTTP_PORT` и раздаёт API и встроенный frontend. Оно не требует установленного на хосте веб-сервера. Nginx в демонстрации масштабирования выполняет только роль сетевого прокси; каждая реплика остаётся самостоятельным HTTP-сервисом.

Доказательство: [`cmd/server/main.go`](cmd/server/main.go), [`web/embed.go`](web/embed.go).

### 8. Параллелизм через модель процессов

Можно запустить несколько одинаковых экземпляров сервера. Они используют общую БД и JWT-ключ; авторизация и прикладное состояние доступны любой реплике. Дополнительный Compose-файл убирает фиксированный порт хоста у app и публикует один порт прокси. `make scale` запускает две реплики; миграции остаются отдельной задачей.

Доказательство: [`docker-compose.scale.yml`](docker-compose.scale.yml), [`deploy/nginx.conf`](deploy/nginx.conf). Это демонстрация масштабирования web-процесса, а не отказоустойчивого кластера PostgreSQL: в учебном стенде экземпляр БД один.

### 9. Быстрый запуск и корректное завершение

При старте запускается готовый бинарник, подключается пул к БД; генерации, компиляции и миграций в web-процессе нет. Начальное подключение ограничено таймаутом. SIGTERM включает завершение работы, останавливает приём новых соединений и даёт активным запросам до 10 секунд. При превышении таймаута запросы отменяются, соединения закрываются; очистка пула ограничена ещё двумя секундами. Compose даёт процессу 15 секунд. Незавершённые транзакции БД откатываются.

`/healthz` показывает жизнеспособность процесса, `/readyz` проверяет доступность БД с таймаутом и возвращает 503 при завершении/недоступности БД.

Доказательство: [`cmd/server/main.go`](cmd/server/main.go), [`internal/app/app.go`](internal/app/app.go).

### 10. Паритет окружений

Для разработки, проверки и развёртывания используется PostgreSQL, а не отдельная облегчённая СУБД. Один Dockerfile задаёт одинаковые зависимости и runtime, готовый образ переносится между окружениями. E2E-тесты работают с реальным PostgreSQL через Testcontainers. Различия настроек задаются через env. Отдельные staging/production-контуры в рамках этого ДЗ не развёрнуты; процесс их подготовки использует тот же артефакт и стек.

### 11. Логи как поток событий

Сервер и мигратор пишут структурированные JSON-логи в stdout. HTTP-логирование включает метод, путь, статус и длительность; токены и тела запросов в access-log не записываются. Приложение не открывает локальные файлы логов и не занимается ротацией. Docker собирает поток; централизованный сбор можно добавить в следующих ДЗ без изменения бизнес-кода.

Доказательство: [`internal/middleware/logging.go`](internal/middleware/logging.go), [`cmd/server/main.go`](cmd/server/main.go), [`cmd/migrate/main.go`](cmd/migrate/main.go).

### 12. Административные задачи как одноразовые процессы

Мигратор `/app/migrate up` находится в том же образе, что и сервер. Он использует тот же код, SQL-миграции и настройки окружения. Compose запускает его как одноразовый контейнер перед приложением; отдельно доступна команда `make migrate`. Ошибка миграции завершает процесс с ненулевым кодом и препятствует запуску приложения. Уже выполненные миграции повторно не изменяют схему.

Доказательство: [`cmd/migrate/main.go`](cmd/migrate/main.go), [`internal/migrations/embed.go`](internal/migrations/embed.go), [`docker-compose.yml`](docker-compose.yml).

## Воспроизведение

Инструкции запуска, тестов, проверки сохранности данных и двух реплик находятся в [`README.md`](README.md). Основной сценарий: `make env`, `make build`, `make up`, затем открыть <http://localhost:8080>.

Архив создаётся после коммита командой `make archive`. Он содержит полный исходный код, спецификацию и SQL для воспроизводимой генерации, Dockerfile, Compose, инструкции и этот отчёт. Секреты, Git-метаданные, бинарники и данные БД в архив не входят.

## Результаты проверки

Проверено локально 2 октября 2026 года:

- Docker-образ успешно собран, runtime работает от UID 65532 с read-only filesystem.
- Unit-тесты конфигурации, probes, HTTP-логирования и исходных модулей проходят. Проверено, что логгер не изменяет тело запроса и не записывает секреты.
- 21 E2E-тест с PostgreSQL 18.3 проходит, включая CRUD, права доступа, промокоды, остатки и одновременную отмену одного заказа. Два параллельных запроса отмены возвращают 200 и 409; остаток восстанавливается один раз.
- HTTP smoke проходит на одном экземпляре, напрямую между двумя репликами и через балансировщик Nginx. Проверены общая авторизация, обновление токенов, CRUD и операции с заказом.
- После `docker compose down` и повторного `up` сохранённые аккаунт, изменённый/архивированный товар и отменённый заказ доступны с прежними значениями. Том БД не удалялся.
- При SIGTERM сервер записал завершение graceful shutdown и вышел с кодом 0.
- В Chromium через Playwright 1.58.2 пройдены 15 браузерных проверок: регистрация, вход, создание, редактирование и архивирование товара, фильтры, карточка, сохранение сессии и refresh. При ширине 1440 и 390 пикселей нет горизонтального переполнения и ошибок JavaScript.

Эти проверки подтверждают работоспособность учебного стенда. Они не являются нагрузочным тестированием, аудитом безопасности или доказательством высокой доступности БД. Нагрузочные тесты, централизованный сбор метрик/логов и отказоустойчивый PostgreSQL можно добавлять в последующих заданиях.

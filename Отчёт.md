# Отчёт: Маркетплейс

## Доменная область

Приложение представляет собой небольшой маркетплейс. Продавцы управляют товарами, покупатели просматривают каталог. REST API дополнительно позволяет создавать и изменять заказы, отменять их с возвратом остатков и применять промокоды.

Веб-интерфейс включает регистрацию и вход, создание товара, просмотр списка и карточки, редактирование, архивирование и восстановление. В каталоге доступны фильтры по статусу и категории, а также пагинация.

Удаление товара логическое: `DELETE /products/{id}` устанавливает статус `ARCHIVED`. Товар остаётся в истории заказов и доступен через фильтр архива. При регистрации можно выбрать роль покупателя или продавца. Покупатель просматривает каталог, продавец может создавать товары и изменять свои.

## Стек и архитектура

- Бэкенд: Go 1.26, HTTP/1.1 REST, chi, pgx, sqlc, oapi-codegen, golang-migrate, zerolog.
- Фронтенд: HTML, CSS и JavaScript. Файлы встроены в Go-бинарник через `go:embed` и обращаются к API на том же адресе.
- Хранилище: PostgreSQL 18.3. Пароли пользователей хешируются bcrypt, refresh-токены хранятся в виде хешей.
- Сборка и запуск: многостадийный Dockerfile и Docker Compose. Приложение и PostgreSQL работают в отдельных контейнерах, миграции выполняются одноразовым процессом перед запуском сервера.
- Масштабирование: дополнительная конфигурация Compose запускает две реплики сервера за Nginx.

## Основные сущности

| Сущность | Назначение |
|---|---|
| Пользователь | Email, хеш пароля, роль USER/SELLER/ADMIN |
| Товар | Владелец-продавец, название, описание, категория, цена, остаток, статус |
| Заказ | Покупатель, статус, общая стоимость и скидка |
| Позиция заказа | Связь заказа с товаром, количество, цена на момент заказа |
| Промокод | Процентная или фиксированная скидка, срок действия и лимит использований |

Схема и ограничения описаны в [SQL-миграции](internal/migrations/000001_init.up.sql), запросы — в [internal/db/queries/](internal/db/queries/).

## Соответствие 12 факторам

Приложение построено по принципам [The Twelve-Factor App](https://12factor.net/ru/).

### 1. Кодовая база

Исходники фронтенда и бэкенда, миграции и конфигурация запуска хранятся в одном Git-репозитории. Версия приложения определяется коммитом; для развёртывания в разных окружениях используется общая кодовая база.

### 2. Зависимости

Зависимости Go объявлены в [go.mod](go.mod), контрольные суммы зафиксированы в [go.sum](go.sum). Версии генераторов oapi-codegen и sqlc, компилятора и базовых образов закреплены в [Dockerfile](Dockerfile). Генерация и компиляция выполняются внутри Docker, готовый образ содержит всё необходимое для запуска. Файлы фронтенда поставляются вместе с приложением.

### 3. Конфигурация

Адрес БД, JWT-ключ, порт, сроки действия токенов, уровень логирования и таймауты читаются из переменных окружения. [Загрузчик конфигурации](internal/config/config.go) проверяет обязательные настройки и их значения до запуска сервера. [.env.example](.env.example) описывает настройки, а команда `make env` создаёт локальный `.env` со случайными секретами. Этот файл исключён из Git, контекста сборки Docker и архива исходников.

### 4. Сторонние сервисы как подключаемые ресурсы

PostgreSQL работает отдельно от приложения и подключается по `DB_DSN`. Для перехода на другой экземпляр PostgreSQL достаточно подготовить схему миграциями и изменить строку подключения. [Подключение к БД](internal/db/db.go) не привязано к конкретному серверу или способу его развёртывания.

### 5. Сборка, релиз, запуск

Сборка генерирует Go-код, компилирует сервер и мигратор, встраивает фронтенд и SQL-миграции в бинарники. Релиз состоит из готового образа с тегом версии и конфигурации окружения. При запуске используется этот образ. Стадии разделены командами [Makefile](Makefile): `make build VERSION=1.0.0` собирает образ, `make up VERSION=1.0.0` запускает его. Образ содержит метки версии и ревизии исходников.

### 6. Процессы без локального состояния

Товары, пользователи, заказы, refresh-токены и история операций хранятся в PostgreSQL. Память сервера используется для конфигурации, соединений и временных данных запросов. Реплики не хранят пользовательское состояние на локальном диске и могут перезапускаться независимо; данные и авторизация доступны через общую БД.

### 7. Привязка портов

[Go-сервер](cmd/server/main.go) самостоятельно слушает HTTP-порт, заданный переменной `HTTP_PORT`, и обслуживает API и [встроенный фронтенд](web/embed.go). Каждая реплика доступна как самостоятельный HTTP-сервис.

### 8. Параллелизм через модель процессов

Приложение масштабируется запуском нескольких одинаковых экземпляров сервера. Реплики используют общие PostgreSQL и JWT-ключ, поэтому запросы одного пользователя могут обрабатываться любой из них. Команда `make scale` запускает две реплики через [дополнительный Compose-файл](docker-compose.scale.yml), а [Nginx](deploy/nginx.conf) распределяет запросы между ними.

### 9. Быстрый запуск и корректное завершение

При старте запускается готовый бинарник и создаётся пул соединений с БД. Время начального подключения ограничено таймаутом. При `SIGTERM` [сервер](cmd/server/main.go) прекращает принимать новые соединения и даёт активным запросам завершиться в пределах `SHUTDOWN_TIMEOUT` — по умолчанию 10 секунд. После этого соединения закрываются.

[Проверки состояния](internal/app/app.go) доступны по HTTP: `/healthz` показывает, что процесс работает, а `/readyz` проверяет доступность БД и возвращает `503` при её недоступности или завершении сервера.

### 10. Паритет окружений

Для локального запуска и интеграционных тестов используется PostgreSQL 18.3. [Тесты](internal/e2e/) поднимают базу через Testcontainers. [Dockerfile](Dockerfile) фиксирует зависимости и среду выполнения; собранный образ можно использовать в разных окружениях, передавая их настройки через переменные окружения.

### 11. Логи как поток событий

Сервер и мигратор пишут структурированные JSON-логи в stdout, откуда их собирает Docker. [HTTP-логирование](internal/middleware/logging.go) включает метод, путь, статус и длительность запроса. Токены и тела запросов в лог не записываются. Хранением и ротацией логов управляет среда запуска.

### 12. Административные задачи как одноразовые процессы

[Мигратор](cmd/migrate/main.go) находится в том же образе, что и сервер, и использует общие SQL-миграции и настройки окружения. [Compose](docker-compose.yml) запускает его как одноразовый контейнер перед приложением; отдельно доступна команда `make migrate`. Ошибка миграции завершает процесс с ненулевым кодом и препятствует запуску приложения. Уже выполненные миграции повторно не изменяют схему.
